# Overview

Walkingen uses an **Action-First Calm** visual direction. The interface should make the next safe action obvious without looking competitive, clinical, or visually noisy. It is designed first for one person using a Samsung Galaxy S23, while remaining understandable to older and non-technical users.

The visual hierarchy is intentional:

1. One dominant action for the current context.
2. The current state in plain language.
3. Supporting progress or history.
4. Detail only when the user asks for it.

Material 3 is the implementation foundation. Android wallpaper-derived dynamic color is not used in the initial product. `DESIGN.md` owns visual tokens and visual rationale; product behavior, screen flow, Android lifecycle, and persistence remain in their dedicated product, domain, ADR, and testing documents.

# Colors

The palette is generated by Flutter `ColorScheme.fromSeed` from the fixed calm green seed `#4F6F52`. The values above were measured from the pinned Flutter 3.47.1 implementation and are the visual contract for the current foundation.

- Use `primary` only for the highest-emphasis action and selected emphasis.
- Use `primary-container` for selected navigation and calm highlighted areas.
- Use `surface` for the application background and `surface-container` for grouped supporting content.
- Use `error` for error text and destructive/error state emphasis, always accompanied by text and, where useful, an icon.
- Light, dark, and system modes are all supported. A component added to one brightness must define and verify the other brightness.
- Never assign future walking states such as success, paused, warning, excluded, or interrupted to arbitrary colors. Add semantic tokens only in the slice that introduces the state, with contrast evidence and non-color cues.

# Typography

Walkingen uses the Android system Roboto family through Flutter Material 3; no bundled custom font is required. The token values mirror Flutter's Material 2021 English-like type scale.

- `headline-medium`: primary walk metrics when a metric must dominate.
- `title-large`: screen and major section titles.
- `body-large`: primary explanatory and form content.
- `body-medium`: supporting content, helper text, and validation text.
- `label-large`: buttons and navigation labels.

Text must remain usable with system scaling. Do not force a fixed text scale, clip text, or rely on a single horizontal row when content can wrap or reflow vertically. Turkish and English copy may have different lengths; both are first-class layouts.

# Layout

Use a 4 logical-pixel base grid and prefer the defined spacing tokens. The normal page inset begins at `spacing.md`; larger separations should express hierarchy rather than decorate empty space.

- Every interactive target is at least the 48×48 logical-pixel `minimumTouchTarget`; controls must grow rather than clip when scaled text needs more room.
- A narrow 320×640 logical-pixel viewport at 2× text scale is a required regression surface for navigation and critical forms.
- Keep the primary action reachable and visually distinct.
- Prefer vertical reflow over shrinking text or compressing touch targets.
- Active-walk screens prioritize the map, large duration and distance, then smaller pace and step metrics.

# Elevation & Depth

Use Material 3 default elevation unless a tested interaction requires otherwise. Prefer surface tone, spacing, and typography hierarchy over stacks of shadows. Do not add decorative elevation to every card.

# Shapes

Use the small set of rounded tokens above when a slice requires an explicit component shape. Do not introduce a new radius for a single screen. Native Material controls may retain their Material 3 default shape until a reusable Walkingen component deliberately overrides it.

# Components

## Primary action

A screen has at most one high-emphasis primary action. On the Home screen this is **Start Walk / Yürüyüşü Başlat**. On a paused walk it is **Resume / Devam et**. Secondary or destructive actions must not compete visually with it.

## Navigation

Normal navigation contains Home, History, and Profile/Settings. Labels remain short in the navigation surface (`Profile` / `Profil`) while content headings may be more descriptive. Selected state uses icon, label, and container treatment; it never depends on color alone.

## Forms

Profile forms use clear labels, suitable keyboards, concise helper text, and inline plain-language validation. Errors appear near their field and are never conveyed only by red color. Draft persistence is behavioral and belongs to domain/persistence specifications, not this visual file.

## Status and supporting surfaces

Use supporting surfaces for weekly progress, empty states, recovery information, and non-dominant summaries. Every walking or record status includes localized text; important states also use an icon. A future slice must define and review semantic state tokens before using status-specific colors.

## Confirmation

Destructive or irreversible actions use strong confirmation with concrete context. Walk completion and permanent deletion remain different actions. Confirmation hierarchy follows the approved product flow rather than inventing a visual shortcut.

# Do's and Don'ts

## Do

- Make one next action obvious.
- Use calm natural surfaces and generous but purposeful spacing.
- Keep touch targets at least 48dp and preserve system text scaling.
- Validate light, dark, Turkish, English, and non-color semantics.
- Use encouraging, factual, non-judgmental copy.
- Reuse existing tokens and Material 3 behavior before adding a new visual primitive.
- Update this file in the same PR when a UI slice intentionally changes the visual contract.

## Don't

- Do not use neon fitness aesthetics, competitive dashboards, or dense metric walls on the Home screen.
- Do not show multiple high-emphasis calls to action on one screen.
- Do not communicate success, failure, exclusion, pause, or interruption using color alone.
- Do not shrink text or interaction targets to make a layout fit.
- Do not hard-code user-visible copy outside Turkish/English localization resources.
- Do not derive colors from the Android wallpaper in the initial product.
- Do not add a one-off color, spacing value, radius, or shadow without extending and reviewing the design contract.
